# CHG-296 / U4.1 frozen N-1 to N provider compatibility

This slice qualifies one bounded fact: the unchanged synthetic provider profile
from the frozen N-1 integrated commit still passes the installed public U1
ABI, conformance, and safe-composition boundary on frozen N. The exact inputs
are recorded in
[`environment/u4_n1_provider_compatibility_authority.json`](../environment/u4_n1_provider_compatibility_authority.json).
The two integrated commits both report EPHI version `0.1.0`; they are exact
repository identities, not semantic release tags or Production releases.

`tools/u4_n1_provider_compatibility.py` materializes both commits as clean
detached Git worktrees outside the executing checkout. It prepares each
release's restricted inputs with that worktree's own
`tools/prepare_release_inputs.py`, installs EPHI and the pinned Base wheel in
separate offline virtual environments, and runs each installed release's own
`ephi-release-preflight` before provider installation. It builds and installs
the N-1 synthetic provider wheel in both environments, runs contracts-only
and full composition through each installed `ephi-downstream-preflight`, and
hashes every EPHI distribution-owned file before and after provider checks.
Each full composition uses its own fresh, temporary PostgreSQL database; the
two releases never share a database, so this slice does not run a cross-release
migration or restart.
The N release-input tool emits its own qualification wheel as a side effect;
that unused N-source wheel is recorded and discarded. Only the single N-1
wheel is installed in either environment.
N-1 and N provider-owned source files, safe manifests, and installed provider
files are compared. The installed CLI runs from an external working directory
with no checkout `PYTHONPATH` or `sys.path` entry.

The qualification writes `u4-n1-provider-compatibility.json`, the provider
source manifest and wheel, installed EPHI/provider hash inventories, and the
safe installed preflight reports under an empty external artifact root. It
requires an explicit PostgreSQL 18 DSN for the composition smoke. Full
composition initializes each disposable database independently; this does not
evidence an N-1 to N database migration/restart or retained workflow data. CI
provides its own PostgreSQL 18 service and stores a temporary Actions artifact.
Reusable CI omits `--job-id`; its report and artifact manifest set
`fabric_job` to `null` and `fabric_binding_state` to `UNBOUND_CI`. CI also
asserts `compatibility_state` is `PASS` while confirming that no Fabric job is
bound. For a Project OS Fabric execution, pass that execution's live job ID to
`--job-id`; the report and manifest preserve that exact ID with
`fabric_binding_state` set to `BOUND`. The current R2 staging request is
`ephi-u4-n1-provider-compatibility-fix1`. Stage the exact report and inventories
through the qualified Project OS Artifact Bridge for canonical handoff; a
successful qualification alone is not staging or acceptance.

A PASS is limited to unchanged-provider/public-ABI/core-edit compatibility.
It does not prove database migration/restart across N-1 to N, retained
workflow/read/artifact identity preservation, feature/capability-flag
preservation, failed-upgrade stop-before-promotion, cross-release
activation/rollback, full U4 exit, real company integration, G10, G11, G12,
the Port Gate, release promotion, or Production. U3's same-release
`ephi-release-slot` mechanism is not cross-release compatibility evidence.
