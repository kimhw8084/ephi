# EPHI release/install identity (CHG-258 / U3.1)

This is the first EPHI release/install integration-kit foundation. It identifies
the canonical package and exact installation inputs so an isolated downstream
environment can check what it installed before private providers are composed.
It is packaging and integration evidence; it does not promote a release or
qualify Production.

## Authorities and identity

`src/ephi/release_inventory.json` is generated by
`tools/generate_release_inventory.py`. Its versioned schema binds:

- distribution, version, Python range, canonical `ApplicationIdentity`, and
  hashes for every installed EPHI package file;
- exact NiceGUI Base repository, Git commit, framework version, and NiceGUI
  version from `environment/nicegui_base_runtime.json` and `pyproject.toml`;
- exact core, PostgreSQL-extra, installer, and build lock identities;
- downstream ABI and provider-contract identities and the six required
  provider categories from `ephi.downstream.contracts`;
- the numbered migration files, byte sizes, per-file SHA-256 values, and
  aggregate identity from the shared O9 migration helper;
- supported packaging claims and explicit `NOT_RUN`/`NOT_CLAIMED`
  qualification boundaries.

Canonical JSON is UTF-8, key-sorted, compact, and ends in one newline. The
`release_identity_sha256` is SHA-256 over the canonical JSON body without that
field. Run `python tools/generate_release_inventory.py --check` to compare it
with its source authorities. Run `--write` only when an authorized source fact
changes.

The install support contract remains `>=3.11,<3.14`. Repository source/package
compatibility checks may include Python 3.14; the release/install preflight
rejects Python 3.14. Core, PostgreSQL-extra, installer, and build requirements
are SHA-256 hashed. The three interpreter-specific lock files are generated
for CPython 3.11, 3.12, and 3.13. The runtime lock carries both Windows and
non-Windows markers; wheel preparation selects artifacts for the connected
preparation host and records its platform identity.

`nicegui-base` remains a VCS dependency at commit
`000298562d6bcbf6df304edbd41b98b30fe4bfcf`. Its wheel is built from that exact
commit using the pinned build-tool lock. The optional `psycopg[binary]==3.3.6`
extra has a separate lock overlay. No new runtime resolver or provider registry
is introduced.

## Restricted-environment flow

1. In a connected upstream environment, check out the exact committed
   candidate with a clean worktree. Choose one supported Python interpreter and
   prepare a new bundle outside the checkout:

   ```bash
   python3.11 tools/prepare_release_inputs.py \
     --output-dir /absolute/staging/ephi-install-inputs
   ```

   The command uses the committed hash locks, downloads only hashed binary
   dependencies from the public PyPI index, checks out the exact Base commit,
   and builds EPHI and Base wheels. It emits `install_inputs.json`, four lock
   files, and a wheelhouse with exact SHA-256 and size records. The transfer
   manifest includes candidate commit/tree, Python/platform, lock identities,
   and an `install_inputs_sha256`. It contains no company secrets, mappings,
   source rows, endpoints, credentials, private indexes, or absolute paths.
   The preparation command prints only bounded JSON facts; it does not print
   subprocess output.

2. Record the prepared `release_identity_sha256` and
   `install_inputs_sha256` through the organization's approved transfer and
   release-digest channel. Transfer the complete bundle using the approved
   company mechanism. Do not copy repository source, credentials, or private
   provider configuration into upstream preparation inputs.

3. In the isolated environment, create a fresh virtual environment using the
   same Python minor version and platform named in `install_inputs.json`. The
   following example uses Python 3.11; for Python 3.12 or 3.13, change `311`
   to `312` or `313` in the lock filenames:

   ```bash
   python3.11 -m venv .venv
   INPUTS=/approved/transfer/ephi-install-inputs
   .venv/bin/python -m pip install \
     --no-index --find-links "$INPUTS/wheelhouse" --require-hashes \
     -r "$INPUTS/locks/installer-py311.txt"
   .venv/bin/python -m pip uninstall -y setuptools wheel
   .venv/bin/python -m pip install \
     --no-index --find-links "$INPUTS/wheelhouse" --require-hashes \
     -r "$INPUTS/locks/runtime-py311.txt"
   .venv/bin/python -m pip install --no-index --no-deps \
     "$INPUTS"/wheelhouse/ephi-*.whl \
     "$INPUTS"/wheelhouse/nicegui_base-*.whl
   ```

   If the optional PostgreSQL adapter is part of the intended installation,
   install the matching overlay as well:

   ```bash
   .venv/bin/python -m pip install \
     --no-index --find-links "$INPUTS/wheelhouse" --require-hashes \
     -r "$INPUTS/locks/postgres-py311.txt"
   ```

   These commands perform no dependency resolution against a network index.
   The bundle and committed lock identities are checked by preflight after
   installation.

4. Before importing or composing private providers, run the release/install
   preflight:

   ```bash
   .venv/bin/ephi-release-preflight --inputs-dir "$INPUTS" --json
   ```

   It fails closed on unsupported Python or implementation, invalid or
   changed release inventory/locks, missing or changed bundle files, a
   different EPHI artifact or package file, dependency/version drift, a wrong
   Base wheel/source identity, migration-set drift, or incompatible downstream
   ABI identity. JSON output and error codes are fixed projections and never
   include the input directory, file paths, environment variables, direct URLs,
   or raw metadata.

5. Run provider conformance and composition separately through the existing
   downstream authority. The release preflight does not load providers:

   ```bash
   .venv/bin/ephi-downstream-preflight \
     --entrypoint approved_package.provider:build_bundle \
     --contracts-only --json
   .venv/bin/ephi-downstream-preflight \
     --entrypoint approved_package.provider:build_bundle --json
   ```

   The first command validates contracts without composing; the second uses
   the existing U1 composition authority. Unknown or incompatible ABI/provider
   majors remain fail-closed.

## Claim boundary

The synthetic downstream package and U1 conformance tests remain the supported
synthetic proof path. The inventory leaves real-family G02/G06, company
identity/TLS, production-like G10 capacity, production RPO/RTO, G12, Port Gate,
company deployment readiness, release promotion, and Production as
`NOT_RUN`/`NOT_CLAIMED`. It does not replace O9 backup/restore, change Product
schema, or qualify a company deployment.
