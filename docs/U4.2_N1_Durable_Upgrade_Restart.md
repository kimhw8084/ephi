# CHG-300 / U4.2 frozen N-1 to N durable upgrade and restart

U4.2 qualifies the frozen N-1 and N installed products against one fresh
PostgreSQL 18 database and one qualification-owned immutable-artifact blob
root. The release, migration, and N-1 provider wheel identities are read from
the integrated U4.1 authority at
[`environment/u4_n1_provider_compatibility_authority.json`](../environment/u4_n1_provider_compatibility_authority.json).
The U4.2 fixture authority stores only its deterministic synthetic workflow,
read, command, artifact, and external-environment identities.

`tools/u4_n1_durable_upgrade_restart.py` materializes both frozen releases as
clean detached worktrees and invokes each worktree's own restricted release
input preparer. It installs each EPHI release and the pinned Base wheel into a
separate virtual environment with no package index. The exact N-1 compatibility
wheel SHA-256 is reused from the U4.1 authority. Provider composition is outside
U4.2, so release-preparation wheel outputs are not treated as compatibility
inputs or installed for provider composition in this proof. Installed preflight
and CLI execution run from an external working directory without checkout
`PYTHONPATH` or import paths.

N-1 applies and verifies its installed migrations, seeds the OPEN fixture
aggregate through the adapter's explicit fixture method, publishes one
historical Episode revision, performs a durable `ClaimEpisode`, and creates an
immutable artifact through `ArtifactService`, `FileArtifactBlobStore`, and
`PostgreSQLArtifactCatalog`. Its process closes the adapter and exits before
the N environment starts. N verifies the unchanged schema first, reapplies the
existing idempotent migration authority, verifies again, then starts a fresh
installed process. It replays the accepted command, checks the exact
historical/live Episode distinction, reads the artifact, and runs bounded
negative controls. The prefix-schema control runs in a second disposable
database and never touches the accepted upgrade database.

The machine report and bounded supporting evidence are written to the supplied
external Artifact Bridge root:

- `u4-n1-durable-upgrade-restart.json`
- `before_upgrade_identity_inventory.json`
- `after_migration_identity_inventory.json`
- `after_restart_identity_inventory.json`
- `migration_restart_summary.json`
- `negative_control_summary.json`
- `artifact-manifest.json`
- `shared-immutable-artifact-blobs/`

For a generic run, omit `--job-id`; the report is marked `UNBOUND_CI`. A live
Fabric run supplies its actual `CF-<24 lowercase hex>` ID and is marked
`BOUND`. The job ID is never written into the committed qualification
authority. An example invocation is:

```bash
EPHI_U4_ADMIN_DSN='<PostgreSQL 18 administrator DSN>' \
  python tools/u4_n1_durable_upgrade_restart.py \
    --artifact-root /external/job/artifact-bridge/material \
    --work-root /external/job/u4-work \
    --repository-root "$PWD" \
    --candidate-sha "$(git rev-parse HEAD)" \
    --candidate-tree "$(git rev-parse 'HEAD^{tree}')"
```

Append `--job-id` only in the live Fabric invocation, using that execution's
actual job ID.

The report's `durable_upgrade_state: PASS` is limited to the frozen N-1 → N
PostgreSQL open/verify/idempotent-apply/separate-process restart proof and the
bounded retained accepted-command, workflow, historical/current-read, and
artifact identities. It does not prove capability-flag preservation,
failed-upgrade stop-before-promotion, cross-release activation or rollback,
full U4 exit, company integration, G10, G11, G12, Port Gate, release
promotion, or Production. A successful local or CI run is not canonical
Project OS handoff until the qualified Artifact Bridge stages and reads back
the exact final candidate evidence.
